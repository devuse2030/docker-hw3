## Резервные копии

Первый прогон создал `backups/countercheck-kwsdzpbz.tar`, второй —
`backups/countercheck-kqcdhbrp.tar`. Архивы хранятся локально вне Docker,
папка `backups/` исключена из Git. Контрольные суммы записаны в
[backup-sha256.txt](backup-sha256.txt).

Для копии приложение и Redis штатно останавливаются, затем вспомогательный
контейнер с read-only доступом к volume выполняет `tar -C /data -cpf - .`.
Архив записывается в файл на компьютере. Только после успешной записи
исходный проект удаляется вместе с volumes. Для восстановления создаётся
новый Redis-контейнер в другом проекте; до его запуска данные распаковываются
через `tar -C /data -xpf -`.

Сохраняются каталог `appendonlydir`, AOF, manifest и RDB-файлы.
В архиве сохранены владельцы UID 999/GID 1000 и права каталогов и файлов.
Успешное чтение счётчика и следующий POST подтверждены в обоих прогонах
после удаления исходного volume.

## Очистка и основное приложение

После завершения обоих прогонов отдельно проверено отсутствие контейнеров,
volumes и сетей всех четырёх тестовых проектов:
[cleanup.txt](cleanup.txt).
Каждый прогон создаёт уникальные имена, свободный порт назначает Docker.
Основной проект `hw_3_solution` и его данные проверочный скрипт не использует.

После проверок ограничения применены также к основному проекту командой:

```sh
docker compose up -d --wait --wait-timeout 90
```

Его счётчик сохранил значение 4: [main-counter.json](main-counter.json).
Параметры: [main-restrictions.txt](main-restrictions.txt).
Статус сервисов: [main-ps.txt](main-ps.txt).

До финальных двух запусков был отдельный пробный запуск, в котором выявлена
и исправлена работа со случайным портом после пересоздания app.
Его вывод сохранён отдельно в `development-failed.log`; к двум успешным
прогонам он не относится. При этой ошибке trap также очистил тестовые ресурсы.
